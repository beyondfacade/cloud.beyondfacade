# commerce BC — 서울시 상권분석서비스 행정동 계열 적재

> 작성 2026-09-23 · 대상 브랜치 `codex/seoul-atlas-landing` · 백엔드 v0.23.0
> 선행 문서: `HANDOFF-260918.md` §4-1(반출 정책), `docs/api.md` §2-1

## 1. 목적

`HANDOFF-260918.md` §1의 세 질문 중 두 개에 실데이터로 답할 수 있게 한다.

- 같은 업종의 점포 수가 늘어날 때 추정매출도 함께 늘어나는가?
- 평일·주말 또는 시간대별 수요가 업종·영업시간 가설과 맞는가? (이번 범위에서는 데이터 확보까지, 분해 지표 적재는 후속)

빅데이터캠퍼스 방문은 하지 않는다. 캠퍼스 카드소비 데이터는 원 수치 반출이 불가하고 응용집계만 가능하다(§4-1). 여기서 쓰는 자료는 전부 서울 열린데이터광장 공개분이며 공공누리 1유형(출처표시, 상업적 이용·변경 가능)이다.

## 2. 확보한 원천 (2026-09-23 다운로드 완료)

`data/raw/seoul_commerce/` — 무결성·SHA256은 같은 경로 `MANIFEST.md`. 루트 `data/`는 git 무시 대상이다.

| 디렉토리 | infId | 파일 | 행 수 | 기간 |
|---|---|---|---|---|
| `sales_adstrd/` | OA-22175 추정매출-행정동 | 연도별 CSV 5 | 343,167 | 2021Q1~2025Q4 |
| `store_adstrd/` | OA-22172 점포-행정동 | 연도별 CSV 5 | 704,470 | 2021Q1~2025Q4 |
| `area_adstrd/` | OA-22160 영역-행정동 | Shapefile | 425 폴리곤 | 스냅샷 |

공통 사항.

- 인코딩 CP949. 연도 컬럼은 `기준_년_코드`가 아니라 **`기준_년분기_코드`** 5자리(`20251` = 2025년 1분기). 20분기 연속, 결측 분기 없음.
- 원천 헤더에 오타가 있다. 시간대 건수 6종이 `시간대_00~06_매출_건수`가 아니라 `시간대_건수~06_매출_건수` 형태다. 이름이 아니라 순서로 매핑해야 한다.
- 점포 쪽은 `개업_율` / `폐업_률`로 표기가 비대칭이다.
- 영역은 CSV가 아니라 ESRI Shapefile이고 좌표계는 EPSG:5186이다. 이번 범위에서는 적재하지 않는다. 행정동 경계는 이미 브이월드 WFS로 확보돼 있다.

## 3. 검증 결과 — 적재해도 되는 근거

### 3-1. 행정동 코드는 붙는다

원천 `행정동_코드`는 8자리, 우리 `region.region_code`는 10자리다. 427개 전부 앞 5자리가 `district_code`와 같고 끝 2자리가 `00`이라, **앞 8자리가 통계청 행정동코드와 1:1**이다. 무손실로 조인된다.

다만 원천은 425개이고 우리와 완전히 겹치지 않는다. 원천이 옛 행정동 체계를 2021~2025 전 분기에 걸쳐 유지하고 있다.

| 원천 코드 | 원천 이름 | 우리 region |
|---|---|---|
| 11230536 | 용신동 | 신설동(1123051500) + 용두동(1123053300) |
| 11680740 | 일원2동 | 개포3동(1168067500) |
| 11740520 | 상일동 | 상일제1동(1174052500) + 상일제2동(1174052600) |

**처리 방침**: 원천 8자리 코드를 그대로 저장하고, `region_code`는 매칭될 때만 기입하는 nullable FK로 둔다. 위 3개 코드는 NULL로 남는다. 용신동을 신설동·용두동으로 쪼개는 안분은 근거가 없으므로 하지 않는다. 결과적으로 우리 427개 동 중 5개는 매출·점포 데이터가 없다. 화면과 리포트에서 이 5개는 "없음"으로 표시하고 0으로 채우지 않는다.

### 3-2. 업종 코드는 9/10 매핑된다

원천 `서비스_업종_코드`는 `CS1NNNNN` 8자리다. **점포 100종, 추정매출 63종**으로 개수가 다르다. 카드매출 추정이 가능한 업종만 매출에 들어간다.

우리 10종 매핑은 다음과 같다. 어린이집은 원천에 대응 업종이 없다.

| 우리 industry_id | 원천 코드 | 매출 존재 | 비고 |
|---|---|---|---|
| academy | CS200001 일반교습학원, CS200002 외국어학원, CS200003 예술학원, CS200004 컴퓨터학원 | CS200004만 없음 | 4:1 — 합산 필요 |
| billiard | CS200016 당구장 | 있음 | 1:1 |
| cafe | CS100010 커피-음료 | 있음 | **주의: 아래 참조** |
| convenience_store | CS300002 편의점 | 있음 | 1:1 |
| gym | CS200024 스포츠클럽 | 있음 | 근사 — 체력단련장업과 정의가 다름 |
| hair_salon | CS200028 미용실 | 있음 | 1:1. 서브카테고리 네일 CS200029·피부 CS200030은 별도 |
| karaoke | CS200037 노래방 | 있음 | 1:1 |
| pc_bang | CS200019 PC방 | 있음 | 1:1 |
| real_estate | CS200033 부동산중개업 | 있음 | 1:1 |
| childcare | 없음 | 없음 | 원천에 대응 업종 부재 |

**확정되지 않은 두 건**을 명시한다.

- `cafe`: 우리 cafe는 인허가 휴게음식점(`rest_cafes`)이 원천이다. 휴게음식점은 법적으로 제과점·패스트푸드·분식을 포함하므로, 원천의 CS100005 제과점·CS100006 패스트푸드점·CS100008 분식전문점까지 묶어야 모집단이 맞을 수 있다. 기본값은 CS100010 커피-음료 단독으로 두되, 교차검증(§6)에서 점포 수 괴리를 보고 재조정한다.
- `gym`: 우리 gym은 인허가 체력단련장업이다. 원천의 스포츠클럽이 가장 가깝지만 골프연습장·볼링장이 별도 코드로 있어 정의가 정확히 겹치지 않는다.

**확정 (2026-09-23 교차검증)** — 상세 근거는 `2026-09-23-commerce-crossvalidation.md`.

| 업종 | 확정 매핑 | 적합도 |
|---|---|---|
| cafe | CS100010 커피-음료 + CS100006 패스트푸드점 + CS100008 분식전문점 | 비율 1.242 · r 0.930 |
| gym | CS200024 스포츠클럽 단독 | 세 지표 모두 최적 |
| hair_salon | CS200028 미용실 + CS200029 네일숍 + CS200030 피부관리실 | 비율 1.103 · r 0.987 (전 업종 최고) |

제과점은 뺀다. 식품위생법상 별개 영업종류이고, 우리 cafe 36,891개 중 대형 제과 프랜차이즈는 15개뿐이다. 설계 초안의 확장안(제과 포함)은 비율 1.435로 과대하다.

`hair_salon`은 당초 1:1로 뒀으나 우리 미용업 안에 네일 3,972개·피부 2,176개가 실제로 있어 3코드 합산이 맞다.

**비교에 쓸 수 없는 업종 3종**: academy 1.86 · real_estate 2.03 · pc_bang 0.31. 원인은 행정동 미기입이 아니라(영업중 기준 최대 2.1%p) academy·real_estate의 폐업 이력 0건과 pc_bang의 폐업 미신고다. `real_estate`는 매출 커버리지가 6.9%에 불과해 위 표의 "매출 있음" 표기도 실질적으로는 거의 없음에 가깝다.

이 두 건 때문에 **매핑을 사실 테이블에 박아 넣지 않는다**. 매핑은 기존 `industry_source_code`(UK가 `industry_id, source_system, code`라 N:1을 이미 지원한다)에 `source_system='seoul_commercial'` 행으로 넣고, 사실 테이블은 원천 코드만 들고 조인한다. 매핑을 바꿔도 재적재가 필요 없다.

## 4. 테이블 설계

새 BC `apps/commerce/`. 테이블 2개이므로 프랙탈 세트 2벌이다. 라우터는 이번 범위에서 만들지 않는다. `convenience`·`childcare` 전례를 따라 entity·ORM·ports·interactor·gateway·repository·CLI까지 구성하고 라우터는 후속으로 둔다.

### 4-1. `region_commerce_sales` — 추정매출

```
PK(adstrd_code, service_industry_code, year_quarter)

adstrd_code            varchar(8)   원천 행정동_코드 원본
service_industry_code  varchar(8)   원천 서비스_업종_코드 원본
year_quarter           varchar(5)   원천 기준_년분기_코드 '20251'
region_code            FK → region  nullable — 앞 8자리 일치 시 기입
sales_amount           bigint       당월_매출_금액
sales_count            bigint       당월_매출_건수
```

`region_code`를 실제 FK로 들고 있는 것은 의도적 역정규화다. 근거는 두 가지다. 8자리와 10자리를 `left()`로 조인하면 인덱스를 못 타고, ERD 규칙상 모든 테이블은 엣지로 연결돼야 한다(§13).

`industry_id`는 **저장하지 않는다.** `industry_source_code`를 거쳐 조인한다. §3-2의 미확정 매핑을 재적재 없이 바꾸기 위해서다.

요일·시간대·성별·연령대 분해 47개 컬럼은 이번 범위에서 적재하지 않는다. 원본 CSV를 보관하고 있어 나중에 재파싱하면 되고, 지금 필요한 질문에는 총액·건수만 있으면 된다. 적재할 경우 1NF를 지켜 wide 53컬럼이 아니라 `(dim_type, dim_key, amount, count)` long 테이블로 분리한다.

### 4-2. `region_commerce_store` — 점포

```
PK(adstrd_code, service_industry_code, year_quarter)

adstrd_code                  varchar(8)
service_industry_code        varchar(8)
year_quarter                 varchar(5)
region_code                  FK → region  nullable
store_count                  int    점포_수 — 프랜차이즈 제외값
similar_industry_store_count int    유사_업종_점포_수 — 프랜차이즈 포함 총 점포수
open_rate                    float  개업_율  (원천 표기 '율')
open_store_count             int    개업_점포_수
close_rate                   float  폐업_률  (원천 표기 '률')
close_store_count            int    폐업_점포_수
franchise_store_count        int    프랜차이즈_점포_수
```

**컬럼 의미 정정 (2026-09-23 교차검증)**. `점포_수 + 프랜차이즈_점포_수 = 유사_업종_점포_수`가 704,470행 전부에서 예외 없이 성립한다. 즉 `점포_수`는 프랜차이즈를 뺀 값이고, 우리 `store` 테이블과 비교할 총 점포수는 **`유사_업종_점포_수`**다. 편의점이 결정적이다. `점포_수` 2,506 대 `유사_업종_점포_수` 8,994이고 우리 보유는 9,395다. 적재된 값 자체는 원천 그대로라 재적재는 필요 없고, 비교·조회 시 어느 컬럼을 쓰는지만 주의한다.

### 4-3. 마스터 보강

`industry_source_code`에 `source_system='seoul_commercial'` 12행을 추가한다. academy 4행 + 나머지 8종 각 1행. childcare는 대응 코드가 없어 넣지 않는다.

## 5. 적재

`apps/commerce/adapter/inbound/cli/load_commerce.py`.

- 원천이 외부 API가 아니라 로컬 파일이므로 게이트웨이는 CSV 리더다.
- CP949로 읽고, 시간대 건수 컬럼은 이름이 아니라 순서로 잡는다(§2 오타).
- `region_code` 해석은 `region` 427행을 앞 8자리 키로 한 번 읽어 메모리 맵으로 처리한다. 행마다 조회하지 않는다.
- PK 기준 `INSERT … ON CONFLICT DO UPDATE`로 멱등하게 만든다. 재실행해도 행이 늘지 않아야 한다.
- 결측·비정상 값은 0으로 채우지 않고 NULL로 보존한다. childcare BC의 `EW_CNT_TOT` 처리 선례를 따른다.

## 6. 교차검증 — 적재 후 반드시 확인할 것

1. **행 수**: sales 343,167 · store 704,470이 그대로 들어갔는가. 분기 20개가 전부 있는가.
2. **region 해석률**: 3개 코드만 NULL이고 나머지는 전부 기입됐는가.
3. **모집단 괴리**: 같은 동·업종·연도에 대해 상권분석서비스 `점포_수`와 우리 `region_industry_metric.store_count`를 비교한다. 우리 store는 `region_code` NULL이 11.5%라 동 단위 집계에서 그만큼 빠지고, academy는 폐업 이력이 0건이다. 이 괴리를 수치로 기록한다.
4. **cafe·gym 매핑 판정**: 3의 괴리가 cafe에서 유독 크면 §3-2의 확장 매핑(제과점·패스트푸드·분식 포함)으로 다시 계산해 어느 쪽이 맞는지 판단한다.
5. **HANDOFF 첫 질문 시범 답변**: 대표 동 몇 곳 × 한 업종으로 "점포 수가 늘 때 추정매출도 늘었는가"를 실제로 계산해 본다.

**하지 않을 것**: 추정매출을 점포 수로 나눈 값을 '점포당 실제 매출'로 제시하지 않는다. 두 데이터의 모집단이 같다는 보장이 없다(HANDOFF §5-3).

## 7. 범위 밖

- 생활인구(OA-14991)와 길단위인구(OA-22178). 별도 작업으로 돌린다.

- 영역 Shapefile 적재. 행정동 경계는 브이월드로 이미 확보돼 있다.
