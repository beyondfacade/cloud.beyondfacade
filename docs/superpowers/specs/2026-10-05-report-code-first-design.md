# 리포트 구조 변경 — 사실은 코드, 해석은 LLM 한 단락 (설계)

- 날짜: 2026-10-05
- 브랜치: `feat/report-code-first` (기반 `feat/report-eval150`, 평가셋 150건 포함)
- 버전: backend v0.68.0, frontend 다음 minor(Codex 위임)
- 상태: 사용자 승인 설계(대화), 스펙 검토 대기

## 1. 배경과 목표

LLM 평가(10/4~10/5)와 평가셋 150건 판정에서 드러난 것:

- 운영 Gemini 리포트의 핵심 오류율이 150건 기준 26.7%(LLM 판정, 95% 구간 19.8~34.5%)였다. 12건 평가의 "0건"은 표본이 작아서였다.
- 오류의 대부분은 모델 능력이 아니라 **사실을 글로 옮기는 과정**에서 생겼다 — 수치 오귀속(서울 동 상권 전체 기준값 118개월을 업종 수치처럼), 대안 등급 바꿔 쓰기, 시간대(hour_gap) 해석 뒤집기, 지원사업 제목 변형.
- 사람이 사실 묶음과 대조해도 판단하기 어려웠다(사용자 피드백) — 데이터가 부족한 곳(판정 보류·일부 판정 업종·표본 부족)과, 숫자는 있으나 무엇의 숫자인지 알기 어려운 곳 둘 다. 사람이 판단하기 어려운 문장은 사용자도 판단할 수 없다.
- 화면은 이미 섹션마다 사실을 코드로 그린다(판정 카드·신호 막대·폐업률 추이·동네 특성·영업 지속·외부 충격·유사 사례·시간대 막대·시간대 차이 차트·대안 카드·지원사업 카드). LLM 글은 이를 다시 옮기다 틀린다.

목표: **결론과 수치는 모두 코드가 사실에서 쓰고, LLM은 질문에 대한 답(질문이 없으면 총평) 한 단락만 쓴다.** 리포트 본문은 검증할 필요 없이 결정적이 되고, LLM이 틀릴 수 있는 범위는 숫자 없는 한 단락으로 줄어든다.

비목표: 사실 수집·판정 로직·화면 차트/카드·의도 관문·자금 계획 변경. 같은 질문 캐시(다음 단계).

## 2. 결정 사항 (사용자 확정)

| 결정 | 내용 |
|---|---|
| LLM 범위 | 맨 위 `answer` 한 단락(3~5문장)만. 6개 섹션은 전부 코드 |
| 질문 없음 | LLM이 총평 한 단락("이 동네에서 이 업종을 한다면 먼저 볼 것") — 화면 구성은 질문 유무와 무관하게 같다 |
| 도구 호출 | 리포트 경로에서 제거 — 리포트와 자금 계획은 별개 화면이고, 평가 252회에서 도구 호출 0회 |
| 샘플링 | 온도 0·seed 42 유지(`report_sampling.py`) |
| 캐시 | 범위 밖(다음 단계) |

## 3. 리포트 구성과 SSE

```
answer        ← LLM 한 단락 (숫자 금지)
verdict       ← 코드  "판정"
reasons       ← 코드  "왜 안 되나"
analogs       ← 코드  "유사 사례"
conditions    ← 코드  "그래도 한다면"
alternatives  ← 코드  "대안 동네·업종"
funding       ← 코드  "대안 업종 지원사업"
```

이벤트 순서(기존 계약 유지 + `answer` 추가):

1. `agent_status`·`facts` — 지금과 같다.
2. 코드 섹션 6개를 `report_delta {section, markdown}`로 **즉시** 내보낸다(섹션당 한 조각). 사실 수집이 끝나면 본문이 바로 뜬다.
3. LLM `answer`를 모았다가 가드 검사 후 `report_delta {section: "answer", markdown}`로 내보낸다(§5).
4. `report_done` — 지금과 같다. 인용(citations)은 사실 묶음에서 코드가 만든 것만(도구 인용 제거).

저장: 저장 리포트(`analysis_repository`)에 `answer` 섹션이 추가된다. **옛 저장 리포트(answer 없음)도 그대로 열려야 한다.**

## 4. 코드 섹션 문장 — `apps/agent/domain/services/report_sections.py` (순수 모듈)

기존 `report_fallback.py`의 `verdict_markdown`·`analogs_markdown`·`alternatives_markdown`를 정식 본문으로 옮기고, 나머지 세 섹션을 새로 쓴다. 섹션 이름 → 작성 함수 표(dict 디스패치). 원칙:

1. **모든 숫자에 범위를 붙인다.** 무엇의(업종/동 전체/서울 기준값), 어디의(이 동/서울), 언제의(기간·분기). 예: "서울 동 상권 전체 기준(업종 무관) 영업 중 점포 평균 118개월".
2. **자료가 없으면 "자료 부족 — 이유"를 쓴다.** `available: false`의 `reason`, 표본 부족 신호, 일부 판정 업종(편의점·어린이집 등)이 해당. 빈칸을 추정으로 채우지 않는다.
3. **신뢰 태그는 코드가 붙인다.** 정형 값 `[확인된 사실]`, 뉴스·검색 `[참고 신호]`. 기본 태그 가드(`LeadingTagGuard`)는 코드 섹션에 쓰지 않는다(태그가 이미 정확하다).
4. 화면 차트와 같은 규칙을 쓴다 — 시간대 문장은 프론트 `hour-gap-sentence.ts`와 같은 규칙(두 최대 구간의 위치로 말한다)을 백엔드에 옮기고 같은 입력에 같은 문장을 내는지 테스트로 고정한다.

| 섹션 | 쓰는 것 |
|---|---|
| 판정 | 등급 라벨 + 켜진 신호 수(강 신호 수), 판정 불가면 이유 |
| 왜 안 되나 | 켜진 신호마다 `evidence` 한 줄(참고 신호는 "참고"로), 폐업률 추이(연도·업종 범위 명시, 2020~2022 왜곡 가능성 고지 — 규칙 ②), 외부 충격(전 업종 공통 여부) |
| 유사 사례 | 기존 기준 문장(`analog_sentences`) + 최근 뉴스(`[참고 신호]`, 없으면 "관련 최근 뉴스 없음"을 쓰지 않고 줄을 생략) |
| 그래도 한다면 | 시간대 문장(사람·돈이 몰리는 구간), 동네 유형·피크/저점, 상권 영업 기간(범위 명시), 예산이 있으면 "자금 계획 화면에서 계산" 안내 한 줄 |
| 대안 | 두 축 각 최대 3개, 등급 라벨 그대로(기존 `alternatives_markdown`) |
| 지원사업 | 공고 제목(원문 그대로)·기관·마감, "자격 확정이 아니라 해당 가능성", 금리·한도 예상치 고지(규칙 ③) |

## 5. LLM 답변 — `answer`

- 입력: 시스템 프롬프트(짧게) + 사용자 메시지 = 질문(없으면 총평 지시) + **코드가 쓴 6개 섹션 문장 그대로**. 원본 facts JSON을 넘기지 않는다 — 화면에 보이는 것만 근거로 삼게 하고 입력을 약 14k → 2k 토큰대로 줄인다.
- 출력 규칙: 3~5문장, 질문에 직접 답한다. **숫자·링크·공고 번호를 쓰지 않는다.** 판정 등급을 바꾸지 않는다. 규칙 ①(차별 금지)·②(재난기 왜곡)·③(대출 중개·상품 추천 금지) 유지. 자료 부족 섹션을 추정으로 메우지 않는다("자료가 부족해 판단할 수 없다"고 말한다).
- 가드(기존 `report_guards` 재사용 + 하나 추가):
  - 숫자가 든 문장은 지운다(새 가드, 문장 단위 — 한글 문장 끝 기준).
  - 링크·공고 번호 제거(기존 `UrlStripper`).
  - 판정과 모순되는 명시적 등급 단정이 있으면 그 단락 전체를 실패로 보고 다음 모델로 넘긴다(기존 `verdict_contradiction`). 이미 일부를 스트리밍했다면 되돌릴 수 없으므로 `answer`는 끝까지 모았다가 검사 후 한 번에 내보낸다(본문 6개 섹션이 먼저 떠 있으므로 지연 체감이 작다).
- 폴백: Gemini → gemma4:12b(`num_ctx` 그대로) → 둘 다 실패하거나 가드 후 빈 단락이면 코드 한 줄 "질문에 대한 해석을 만들지 못했습니다. 아래 사실을 직접 확인해 주세요."
- 도구 루프·`_FINAL_REQUEST`·도구 인자 검사·도구 인용은 리포트 경로에서 제거. `agent_tools.py`에서 리포트만 쓰던 정의는 정리하되 다른 곳이 쓰는 것(`hit_to_dict` 등)은 남긴다.

## 6. 프론트엔드 (Codex 위임, 작은 변경)

- `shared/api/types.ts` `ReportSection`에 `"answer"` 추가, mock 라우트·픽스처 갱신(§15 계약 테스트).
- `report-view`: `answer`를 맨 위에 "해석" 표시(사실과 구분되는 라벨)로 렌더. 시각 자료 없음. 옛 저장 리포트처럼 `answer`가 없으면 그 블록을 그리지 않는다.
- 6개 섹션 렌더·차트는 그대로. `graded-paragraphs.ts`(유사 사례 태그 재정렬)는 코드 문장이 이미 정확하므로 그대로 두되 깨지지 않는지 테스트만 확인.

## 7. 평가

- 같은 평가셋 150건(`--scenario-set 150`), Gemini·gemma4:12b 각 1회.
- 코드 섹션: 결정적 — 단위 테스트로 고정, 판정 불필요. 150건 전체에 대해 "범위 없는 숫자 0개"·"자료 없음 필드에 추정 문장 0개"를 자동 검사.
- `answer` 자동 지표: 숫자 0개(가드 후), 판정 모순 0, 폴백 비율, 첫 글자·완료 지연(본문은 즉시라 의미가 `answer` 기준으로 바뀜 — 보고서에 명시).
- 사람 검수 20건: `answer` 단락만(3~5문장) — 질문에 답했는가, 사실과 어긋난 말이 있는가. 이전 보정처럼 판단이 어려운지도 기록한다.
- 기준선: 이번 150건 결과(Claude 판정 Gemini 26.7%·12b 80%)와 같은 형식으로 비교하되, 비교 대상이 "리포트 전체"에서 "answer 한 단락"으로 바뀐다는 점을 명시.
