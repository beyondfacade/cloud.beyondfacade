# 모델 평가 — 임베딩·LLM (2026-10-04 ~ 10-05)

> 질문: 한정된 자원에서 얼마나 가성비 있게 모델을 고를 수 있는가. 오프라인(온프레미스)과 온라인을 같은 잣대로 비교한다.
> 장비: RTX 5060 Ti 16GB 1장(CPU 실행도 함께 확인). 보안 요구가 있으면 온프레미스로만 돌려야 할 수 있다.
> 방식: research.remakeday.com/experiments/model-selection 과 같은 순서 — 게이트 먼저, 그다음 품질, 품질이 동률이면 자원(VRAM·지연)이 작은 쪽.

## 2. 목적·제약·원칙

### 자원 제약

- GPU는 RTX 5060 Ti 16GB 한 장이다. 임베딩·리포트 모델·관문 모델이 함께 올라가야 한다.
- GPU가 없는 서버도 고려해 CPU 실행을 따로 쟀다(AMD Ryzen 5 9600X 6코어, RAM 29GB).
- 로컬 모델은 토큰 단가가 없다. 전기료·카드 감가는 계산에 넣지 않았다.

### 외부 API를 쓰는 이유 — 로컬 품질의 한계와 하드웨어 제약

- **로컬 모델의 답을 믿을 수 없다.** 이 서비스의 리포트는 창업 여부라는 돈이 걸린 판단에 쓰인다. 그런데 로컬 후보 6개는 가드를 붙인 뒤에도 엄격 게이트를 하나도 넘지 못했고(§4·§5), 코드 우선 구조(LLM은 해석 한 단락만)로 바꾼 뒤에도 로컬 gemma4:12b의 해석 핵심 오류는 29~34%였다(150건 opus 판정, §11). 숫자·추세·신호 뜻을 본문과 다르게 옮기는 오류라 사용자가 잘못 판단할 수 있다. 그래서 해석은 외부 API(Claude·Gemini)가 쓰고, 로컬은 키가 없거나 외부 호출이 실패할 때의 폴백으로만 둔다.
- **로컬 품질을 올리지 못한 이유는 VRAM이다.** GPU는 RTX 5060 Ti 16GB(16,311 MiB) 한 장이고, 여기에 RAG 임베딩(bge-m3)과 리포트 모델이 함께 상주해야 한다.
  - 지금 폴백인 gemma4:12b(4비트 양자화)는 단독 8,034 MiB, bge-m3와 함께 9,790 MiB다(§4 동시 상주, 리포트 컨텍스트 32,768 기준).
  - 관문 모델까지 따로 올린 조합(e4b + 12b + bge-m3)은 14,661 MiB로 여유가 약 1.6GB뿐이다.
  - 12b보다 큰 모델(27~32B급)은 4비트 양자화 파일만으로 16GB를 넘어 이 카드에 올릴 수 없다(모델 파일 크기 기준 추정, 실측하지 않음). 그래서 후보에서 빠졌고, 같은 이유로 더 큰 모델로 품질을 올리는 길이 막혀 있다.
  - 미세조정·증류로 작은 모델을 맞추는 방법(§9)도 학습에 추론보다 많은 VRAM이 필요해 이 장비에서는 시도하지 못했다.
- 정리하면 로컬 품질의 상한은 "16GB 한 장에 임베딩과 함께 올라가는 12b급"에서 정해지고, 그 상한이 서비스 품질 기준에 못 미친다. 온프레미스가 꼭 필요해지면 GPU 증설(더 큰 VRAM) 또는 별도 추론 서버가 먼저 필요하다.

### 온프레미스 대 온라인

- 온라인(Gemini API)은 같은 지표로 비교만 하고 판정 대상에서 뺐다. 대신 비용(토큰 × 공개 단가, 확인일·URL)과 지연을 적었다.
- 온프레미스 후보는 판정 대상이다. "로컬만으로 운영할 수 있는가"가 이 평가의 핵심 질문이다.

### 판정 규칙

1. 하드 게이트를 통과한 **로컬** 모델만 후보로 남긴다.
2. 주 지표 1위를 고른다(임베딩 MRR, 리포트 품질 점수, 관문 동시 정답).
3. 1위와 후보의 문항별 점수 차이를 paired bootstrap(n=10000, seed 0)으로 구한다. 95% 구간이 0을 포함하면 동률이다.
4. 동률이면 자원이 작은 쪽이다. 임베딩은 낮은 차원 → 짧은 질의 지연, LLM은 VRAM 작은 순 → p95 짧은 순.
5. 현행 운영 모델에 우대는 없다. 단, 임베딩은 "기준선보다 유의하게 좋을 때만 교체"를 규칙에 넣었다.

### 규칙 판정과 사용자 결정이 다른 경우 (임베딩)

- 규칙 판정은 **qwen3@1536 현행 유지**였다. 1위 bge-m3@1024가 기준선보다 유의하게 좋지 않았기 때문이다.
- 사용자는 **bge-m3@1024**로 바꾸기로 했다. 원문 이유는 다음과 같다.
  - "qwen3@1536과 MRR 동률(+0.005 [−0.018, +0.028])이면서 GPU 메모리 664MB 대 4.4GB, 색인·질의를 모델 하나로 처리, CPU로도 운영 가능하다는 점에서 자원 대비 효율이 가장 높다."
  - "위 판정 절의 '현행 유지'는 교체 비용을 고려한 규칙상 결과이고, 자원 제약·온프레미스를 기준으로 한 최종 선택은 bge-m3다."
- 참고로 결정문의 4.4GB는 CPU 측정 표의 qwen3-4b 상주 메모리 값이다. 표에 qwen3의 GPU 상주값은 따로 없다.

## 3. 임베딩 평가 (2026-10-04)

### 후보 9조합

| 구분 | 모델 | 차원 | 구성 |
|---|---|---|---|
| 로컬 | bge-m3 | 1024 | Ollama F16, 색인·질의 같은 모델, instruction 없음 |
| 로컬 | qwen3-embedding-4b | 1536, 2560 | 당시 운영 그대로 — 색인 fp16 / 질의 Ollama Q4 + 질의 프롬프트 |

| API | gemini-embedding-2 | 1024, 1536, 2560 | `task_type`을 받지 않아 프롬프트 프리픽스로 대체 |

- 모델당 한 번만 최대 차원으로 임베딩하고, 앞부분을 잘라 L2 재정규화해 하위 차원을 만들었다(MRL).
- 운영 DB를 건드리지 않고 오프라인 벡터 캐시 + numpy 전수 검색으로 쟀다. HNSW 근사 오차를 빼고 임베딩 품질만 보려는 것이다.
- 로컬 게이트: `gemma4:12b`와 동시 상주 시 밀려나지 않을 것, 질의 p95 ≤ 500ms.

### 평가셋

- 전체 260건을 2026-10-04에 다시 검수했다. **confirmed 233건**(base 179 + hard 54), rejected 27건.
- 재검수에서 질문 22건을 바꿨다(기존 base 16건 + hard 6건: 204·215·227·233·236·249). 118번은 O→X, 258번은 X→O(커밋 18f48f9).
- hard는 세 종류다. colloquial(n=20)은 공고명·핵심어를 피한 창업자 말투, sibling(n=16)은 유사 공고 쌍에서 정답에만 해당하는 조건으로 구별, news_event(n=18)는 헤드라인 단어를 피한 사건 질문이다.
- hard 질문은 ANTHROPIC_API_KEY가 없어 Claude Code 서브에이전트가 쓰고 1차 판정했다. 최종 판정은 사람 검수다.
- 판정 기준은 하나다. 질문만 보고 유사 공고보다 우선해 정답이면 O.
- 기존 질문 16건이 바뀌어 9/24 `evaluate_rag` 수치와 직접 비교하지 않는다.

### 코퍼스

- `rag_chunk` 전량 **8891청크**(sha256 `757b1bbfee5b`). 만료 공고를 포함했다.
- 만료 공고는 운영 검색에서는 빠진다. 여기서는 모든 조합에 같은 방해 문서로 남겼다.

### 지표

- **top-1**: 1순위 결과가 정답인 문항 비율.
- **Hit@5**: 상위 5개 안에 정답이 있는 문항 비율.
- **MRR**: 첫 정답 순위의 역수 평균. 상위 10 기준이다(기존 `evaluate_rag`는 상위 5). 주 지표.
- **nDCG@10**: 상위 10개의 순위 가중 적중(이진 관련도). 보조 지표.
- **MRR(hard)**: hard 54건만의 MRR.
- **p50 / p95 ms**: 질의 임베딩 지연의 중앙값·95백분위. 모델 단위로 쟀다(같은 모델의 차원별 지연은 같다고 본다).

### 판정과 최종 결정

- 로컬(규칙): **qwen3@1536 현행 유지**. 1위는 bge-m3@1024이고, bge-m3@1024·qwen3@1536·qwen3@2560이 동률이다. 기준선 대비 MRR 차 +0.005 [-0.018, +0.028].
- API(규칙): **gemini-001@1024**. 6조합이 모두 동률이라 1024차원 둘 중 p95가 짧은 쪽(426 vs 574ms)을 골랐다.
  - gemini-001@1024와 API 최고 MRR(001@2560)의 차이는 -0.0068 [-0.0156, +0.0001]이다. 구간 상한이 0을 간신히 넘는 경계 동률이다. 이 동률이 없었다면 규칙은 gemini-2@1024를 골랐을 것이다.
  - gemini-embedding-001은 **2028-05-14 단종 예정**이고 가격표에도 없다(https://ai.google.dev/gemini-api/docs/deprecations, 2026-10-04 확인). gemini-2@1024는 001@1024와 동률(MRR 차 +0.0031 [-0.0141, +0.0195])이라, API 경로를 쓰게 되면 gemini-2@1024를 실무 대안으로 검토한다(재색인 1회 약 $0.31).
- API 대 로컬: 기준선 qwen3@1536보다 유의하게 좋은 Gemini 조합은 없다. 001@1024 대비 +0.0187 [-0.0016, +0.0396], 2@1024 대비 +0.0218 [-0.0006, +0.0456]. 둘 다 구간이 0을 포함한다.
- 최종(사용자): **bge-m3@1024**. 이유는 §2에 원문으로 옮겼다. 재색인은 GPU(Ollama)로 했다.

### 채점 방식

자동 지표(전 회차)와 블라인드 LLM 판정자(품질·규칙 위반)를 함께 쓴다.

리포트 지표:

- **품질**: 판정자 점수 = 근거 충실도(1~5) + 자연스러움(1~5), 10점 만점. 주 지표.
- **완주**: 오류 없이 6개 절을 모두 쓴 비율.
- **판정 모순 없음**: facts와 다른 등급을 단정하지 않은 비율.
- **판정 등급 생략**: 판정 절에서 등급 말을 아예 쓰지 않은 회차 수. 생략은 위 지표를 통과하므로 따로 센다.
- **지어내기**: 근거에 없는 숫자가 하나라도 나온 리포트 비율.
- **규칙**: 판정자가 적은 응답 규칙 위반 건수.
- **첫 글자 / 완료 p95**: LLM 호출 시작부터 첫 글자·완료까지 시간의 95백분위(facts 수집 시간 제외).

관문 지표:

- **동시 정답**: 지역·업종이 모두 맞은 비율. 주 지표.
- **지역 / 업종 / 예산**: 각 필드 정답률. 예산은 보조.
- **스키마**: JSON 스키마 통과율.
- **지어내기**: `missing`·`out_of_scope` 26건에서 null이어야 할 칸에 값을 만든 비율.
- **지어내기(null 칸 전체, 참고)**: 정답에 null 칸이 있는 모든 행(51건)을 분모로 센 값.

게이트:

| 역할 | 게이트 |
|---|---|
| 리포트 | 완주 ≥ 0.95 · 판정 일치 = 1.00 · 지어내기 ≤ 0.05 · 응답 규칙 위반 0건 · 첫 글자 p95 ≤ 5초 · 완료 p95 ≤ 60초 |
| 관문 | 스키마 ≥ 0.98 · 지어내기 ≤ 0.05 · p95 ≤ 3초 |
| 자원 조합 | 리포트 모델 + 관문 모델 + bge-m3를 함께 올려 밀려나지 않을 것(`ollama ps` + nvidia-smi) |

판정자 기준표(`data/eval/report_judge_rubric.md`) 요약:

- 판정자는 이름이 가려진 리포트(A, B, C…)를 글만 보고 채점한다. 판정 모델은 opus다.
- `faithfulness`(1~5): 사실 묶음에 있는 사실만 쓰는가. 숫자·공고명·URL 지어내기, 예시값을 현재 사실처럼 쓰기, 판정 등급 바꿔 말하기는 크게 감점.
- `fluency`(1~5): 한국어가 자연스럽고 섹션 계약(판정 1~2문장, 이유는 신호별 단락 등)을 지키는가.
- `violations`: 차별·혐오 표현, 재난기(2020~2022) 폐업률 일반화, 금융 규제(특정 금융사·상품 추천, 대출 권유), 신뢰 등급 표기 규칙 위반.

### 채점 정정 이력

- **판정 일치 → 판정 모순 없음.** 처음에는 기대 등급 표현이 있어야 일치로 봤다. 정상 표현('주의' 등급, `insufficient`, 빨간불, "판정을 내리지 않습니다")을 놓쳐 Gemini가 0.22로 왜곡됐다. "다른 등급을 단정하지 않음"으로 다시 정의하고 동의어를 넓혔다. 생략 회차는 `판정 등급 생략` 열에 따로 적는다.
- **지어내기 근거 확장.** 대조 근거는 facts + 질문 + 도구 결과 + 시스템 프롬프트 + 도구 설명이다. 프롬프트가 준 숫자("13개 입력" 등)를 지어낸 것으로 세지 않으려는 것이다. 시스템 프롬프트의 예시 값을 사실처럼 쓴 경우는 자동 대조로 못 거르므로 판정자에게 맡긴다.
- **관문 지어내기 분모.** 처음 결과는 null 칸이 있는 모든 행(51건)을 분모로 써서 스펙과 달랐고, 그 기준으로는 gemma4:12b가 0.039로 관문 승자였다. 스펙대로 `missing`·`out_of_scope` 26건으로 다시 세면 0.077이고 로컬 관문 승자는 없다. 두 값을 모두 표에 실었다.

### 발견 — 운영 폴백 컨텍스트 잘림

- Ollama 0.31.2는 num_ctx를 지정하지 않으면 입력을 잘라 읽는다. 합성 입력(약 29,400자)을 qwen3.5:4b에 보내자 prompt_eval_count가 기본 컨텍스트에서 2,050, num_ctx 32,768에서 17,422였다. gemma4:12b도 기본 컨텍스트에서 2,051이었다.
- 실제 리포트의 첫 턴 프롬프트는 num_ctx 32,768에서 13.1k~14.1k 토큰이다(도구 없이 최대 13,111, 도구 설명 포함 최대 14,143).
- 운영 로컬 폴백(gemma4:12b)은 그동안 약 2k 토큰만 읽고 facts 대부분을 못 보고 있었다. v0.66.1에서 num_ctx=32768을 지정했고, 호스트·컨테이너 실측 입력이 **2,051 → 19,228토큰**이 됐다(개발 일지 기준).
- 관문 프롬프트는 2,025~2,078 토큰이라 잘리지 않았다. num_ctx 8192를 줘도 같은 값이었다.
- Ollama의 `format`은 Gemini 스키마의 `nullable`을 무시한다(문자열 "null"이 관측됨). Ollama용 스키마는 type 합집합(["string","null"])을 쓴다.

## 5. 코드 가드 적용 후 재평가 (v0.67.0)

화면이 이미 카드로 보여 주는 값(판정 등급·지원사업 원문 링크)을 LLM이 글로 옮기다 틀리는 실패가 많았다. 이것을 코드로 막고 같은 조건(고정 facts 12건, 7개 모델 × 3회, 같은 기준표, 같은 판정 모델)으로 다시 쟀다. 관문은 다시 돌리지 않았다(기준선 캐시 그대로).

### 가드 4종

1. **판정 모순 교체**: 판정 절에 등급 이름을 쓰지 말라고 바꿨다. 명시적 등급 단정이 사실과 어긋나면 코드가 판정 절을 사실 문장으로 바꾼다. 판정 절은 끝까지 모았다가 한 번에 내보낸다.
2. **링크·공고 번호 제거**: 프롬프트에서 쓰지 말라고 하고, 출력 스트림에서도 URL·공고 번호를 지운다.
3. **기본 신뢰 태그**: 판정·이유·조건·대안·지원사업 절 본문이 태그 없이 시작하면 `[확인된 사실]`을 붙인다(유사 사례 절 제외).
4. **지원사업 고지문**: 절 끝에 "금리·한도는 예상치…원문 확인" 고지문을 붙인다.

### 남은 실패 유형

로컬 모델은 여전히 엄격 게이트를 통과하지 못한다. 12b·e4b의 남은 탈락 사유는 규칙 위반과 첫 글자 지연이다. 남은 위반은 가드가 다루지 않은 새 유형이다.

1. **대안 절 등급 바꿔 쓰기** — 대안 동네·업종의 등급(clear 등)을 "판정 없음"·"조건부"로 옮겨 적는다. 12b 12건 중 5건(s03·s07·s08·s11·s12), e4b 2건.
2. **뉴스 없을 때 [참고 신호] 지어내기** — 뉴스가 없는데 프롬프트 예시 문장("대부분 논의·실험 단계라…")을 그대로 옮긴다. 12b 4건, Gemini 2건("기사 없음" 문장).
3. **꺼진 신호를 켜진 신호로 읽기** — e4b 4건. 모델 능력 문제.
4. Gemini의 "예상 대출 금리 연 4.05%" 1건 — 도구 명세의 예시값(`loan_rate` "예 0.0405")이 원인. 온도 0 단계에서 예시값을 지웠다.
5. **기본 태그의 위험** — 코드가 붙이는 `[확인된 사실]`은 문단에 뉴스·추측이 섞여도 붙는다. e4b가 판정·이유 문단에 "최근 뉴스에서는 … 긍정적인 신호"를 섞으면 확인된 사실처럼 보인다(비교 판정에서 4건 지적). 그래서 판정자의 신뢰 등급 표기 위반은 크게 줄지 않았다(e4b 6 → 6, 12b 10 → 7).

## 6. 온도 0·seed 고정 (v0.67.0)

### 원인

- 운영 리포트는 온도를 지정하지 않았다(Gemini 기본 약 1.0, 로컬 모델은 Ollama 기본값).
- 벤치는 로컬만 0.3이었고, "운영과 같게"라는 주석은 틀렸다. LLM 평가 스펙에도 "리포트 0.3(현행과 같게)"로 적혀 있었는데 이 역시 사실과 달랐다.
- v0.67.0에서 운영·벤치 모두 `REPORT_TEMPERATURE=0.0`, `REPORT_SEED=42`(`apps/agent/domain/services/report_sampling.py`) 단일 원천으로 바꿨다. 같은 커밋에서 도구 명세의 `loan_rate` 예시값(0.0405)을 지웠다.
- 재측정은 후보 3개(gemini-2.5-flash, gemma4:12b, gemma4:e4b)만, 고정 사실 12건 × 3회.

### 일관성 지표

같은 모델·같은 시나리오의 3회 반복끼리 비교한다. 1.00이면 완전히 같다.

- **결론 일치**: 회차 간 (완주, 판정 모순 없음, 지어내기 여부)가 모두 같은 시나리오 비율.
- **숫자 일치(Jaccard)**: 회차별 본문 숫자 집합의 겹침.
- **문장 유사도**: 화면 본문끼리의 문자열 유사도(SequenceMatcher).
- **대안 등급 일치**: 대안 절 등급별 항목 수까지 비교(다중집합). 두 회차 모두 대안 등급 줄이 없으면 일치로 세서 값이 조금 부풀 수 있다.

| 모델 | 결론 일치 | 숫자 일치(Jaccard) | 문장 유사도 | 대안 등급 일치 |
|---|---|---|---|---|
| gemini-2.5-flash | 0.75 → **1.00** | 0.42 → **0.71** | 0.39 → **0.74** | 0.75 → **0.94** |
| gemma4:12b | 1.00 → 1.00 | 0.62 → **0.84** | 0.58 → **0.86** | 0.44 → **0.78** |
| gemma4:e4b | 0.83 → **1.00** | 0.34 → **0.79** | 0.40 → **0.82** | 0.22 → **0.72** |

- 왼쪽은 가드 재평가(벤치 설정: 로컬 0.3 · Gemini 기본값), 오른쪽은 온도 0이다.
- 운영 로컬 폴백은 그동안 Ollama 기본 온도로 돌았다. 운영 기준의 실제 개선 폭은 재지 않았다. 로컬 행은 0.3 대비라 운영 기준보다 작게 잡혔을 수 있다.

### 해석

- 세 모델 모두 구간이 0을 포함한다. **유의한 품질 차이는 관측되지 않았다.**
- n=12라 작은 차이는 못 잡는다. e4b 충실도는 −0.25, 하한 −0.58로 경계에 가깝다.
- 같은 회차에 `loan_rate` 예시값 제거가 함께 들어가 있어 온도만의 효과로 볼 수는 없다. 영향은 s11·s12 금리 문장에 한정된다.
- 일관성은 크게 올랐다.
- Gemini는 온도 0에서도 판정 절에 등급 이름을 36건 중 15건 썼다. 모순은 아니지만 프롬프트 준수가 부분적이다.
- 온도 0이어도 완전히 같지는 않다(Ollama·Gemini 모두 결정적이지 않다). 대안 등급이 회차마다 다르게 적히는 경우가 12b 22%, e4b 28% 남았다.
- 같은 질문에 글자까지 같은 답은 캐시(의도 관문 칸 + 사실 기준월 키)로만 보장된다.

LLM:

- 품질 판정자도 LLM이다. 모델명은 가렸지만 문체로 짐작할 수 있다.
- 리포트 시나리오가 12건이라 표본이 작다. 참고 순위의 bootstrap 구간이 넓은 것도 그래서다.
- 지어내기 비율은 하한이다. 대조를 관대하게 했다(프롬프트·도구 설명 숫자도 근거로 인정, 복합 금액 허용폭이 넓음 — 예: "1억 2천만"이 1.25억과도 맞음). 반대로 개월→년 환산 같은 오탐도 일부 있다.
- 252회 실행(7개 모델 × 12 시나리오 × 3회) 전부에서 도구 호출이 0건이었다. s11·s12(규칙·도구 시나리오)도 도구를 쓰지 않았다. EXAONE의 도구 없음 불리함과 도구 결과 근거 대조는 시험되지 않았다.
- 가드 전후 품질은 판정 세션이 달라 ±0.5 안쪽 차이를 판정자 잡음과 구분할 수 없다(참고치).
- 가드 후 첫 글자 p95는 판정 절 버퍼링 시간을 포함해 기준선과 비교할 수 없다.
- 온도 0 비교의 기준선은 운영 설정(기본 온도)이 아니라 벤치 설정(로컬 0.3)이다. 운영 기준 개선 폭은 재지 않았다.
- 온도 0 회차에는 `loan_rate` 예시값 제거가 섞여 있어 온도 효과만 분리할 수 없다.
- 대안 등급 일치는 두 회차 모두 대안 등급 줄이 없으면 일치로 세서 조금 부풀 수 있다.
- e4b의 VRAM은 `size_vram`(3,158 MiB)보다 실제 점유(nvidia-smi 차이 4,871 MiB)가 크다.
- kanana1.5 라이선스는 모델 카드로만 확인했다. 실제로 쓰기 전에 원문 LICENSE 파일을 확인해야 한다.

## 9. 다음 단계

- **리포트 구조 변경** — 결론(판정·수치·대안·지원사업)은 코드가 렌더링하고, LLM은 절별 짧은 해석만 쓴다(온도 0). 같은 질문은 캐시(관문 칸 + 사실 기준월 키)로 같은 답을 준다. 대안 등급 바꿔 쓰기, 첫 글자 지연(12b p95 9.6초, 게이트 5초), 남은 일관성 흔들림을 함께 해결하려는 것이다. 운영 SSE·프론트 영향이 있어 설계 승인을 먼저 받는다.
- 같은 방식의 가드 후보 — 대안 절에도 등급 단정 검사 적용, 뉴스가 비면 [참고 신호] 문장 금지, 뉴스·검색 언급 문단에는 기본 태그를 붙이지 않기.
- **관문 로컬 폴백** — 서울 밖 지명을 서울 동으로 바꾸는 문제를 고친 뒤(규칙 쪽 차단이나 지시문 보강) 다시 잰다.
- **온프레미스용 캐시·증류 검토** — 로컬 단독 운영이 필요해질 경우, 결론을 코드로 옮겨 LLM 부담을 줄이고 캐시로 반복 호출을 없앤다. 그래도 부족하면 Gemini 출력으로 로컬 모델을 맞추는 증류를 검토한다.
- 로컬로 넘어가기 전에는 프롬프트·형식 작업(신뢰 등급 태그 규칙, 공고 번호·URL 처리)을 먼저 하고 다시 잰다.
- API 임베딩 경로를 쓰게 되면 gemini-embedding-2@1024를 검토한다(001 단종 일정).

### 5단계 — 한국어 윤문 규칙(im-not-ai quick-rules 발췌) 시험, 미적용

[말투] 위에 [문장 다듬기] 규칙(번역투·AI 관용구·같은 완곡 표현 반복·문두 접속사·형식명사 끝맺음)을 더해 같은 116건을 쟀다(태그 `polish150`, 브랜치 `feat/answer-polish` v0.77.0, 미머지).

| 모델 | 핵심 오류 말투만 → +윤문 | 짝 비교(말투만에만 / +윤문에만) | 문두 접속사 |
|---|---|---|---|
| gemini-3.8-flash 일반(기본) | 4 (3.4%) → **10 (8.6%)** | 4 / 10 | 72 → 41 |
| claude-opus-5-5 | 4 (3.4%) → 2 (1.7%) | 4 / 2 | 20 → 4 |

- 문장은 깔끔해졌지만 **기본 모델(3.8)의 사실 오류가 늘었다** — 새로 생긴 오류는 본문에 없는 평가·추정을 단정한 것("점포 평균 매출 수준도 높지 않다", "점심 장사에 어울립니다", "카드 결제 외 매출이 많아"를 가능성 아닌 사실로). 완곡 표현·접속사를 줄이라는 규칙이 3.8을 단정 쪽으로 민 것으로 보인다.
- 오퍼스는 오히려 줄었다(4 → 2). 같은 규칙이 모델에 따라 반대로 작용했다.
- 단정 쪽으로 민다고 본 두 규칙(완곡 표현 반복·문두 접속사)을 빼고 번역투·AI 관용구·형식명사 끝맺음만 남겨 다시 쟀다(태그 `polish2-150`): 3.8 **12/116 (10.3%)**(짝 비교 말투만에만 3 · 줄인 윤문에만 11), 오퍼스 4/116(4 · 4). 줄여도 3.8 오류가 줄지 않았다 — 새 오류는 대부분 "시간대 매출 자료 부족인데 유동인구로 매출·장사 시간을 추정"과 "본문에 없는 평가(평균 매출이 높지 않다)"였다. 규칙 내용보다 지시문이 길어지는 것 자체가 3.8의 근거 지키기를 흐리게 하는 것으로 보인다.
- 결정: 두 번 모두 기본 모델 오류가 늘어 **운영에 넣지 않았다**(말투 규칙 v0.76.0까지만 운영). 번역투·AI 관용구는 말투 규칙만으로도 이미 0건이다. 브랜치 `feat/answer-polish`는 기록으로 남기고 머지하지 않는다.
- 모델별 지시문(Gemini는 말투만, 오퍼스는 말투+윤문)도 검토했으나 넣지 않았다(사용자 결정 2026-10-06) — 오퍼스는 폴백이라 실제로 쓰는 리포트가 1% 안팎(운영 기록 약 130건 중 폴백 1건)이고, 오퍼스 4 → 2건 개선은 판정 오차(±3건) 안이다. 오퍼스 사용이 늘거나 반복 측정으로 개선이 확인되면 다시 본다.

### 6단계 — 시간대 매출 자료 없음을 코드 문장으로 명시, 미적용

남은 오류 중 가장 많은 "시간대 매출 자료가 없는데 유동인구로 매출·장사 시간을 추정"을 지시문이 아니라 코드가 쓰는 사실 문장으로 막아 봤다(태그 `hours150`, 브랜치 `feat/hour-gap-missing`, 미머지). 시간대 자료 부족 줄 끝에 "이 업종이 어느 시간대에 매출을 내는지는 알 수 없습니다", 사람 흐름 줄에 "(동 전체 유동인구, 업종 매출과 다름)".

| 모델 | 핵심 오류 말투만(운영) → +시간대 명시 | 그중 시간대 관련 | 짝 비교(전에만 / 후에만) |
|---|---|---|---|
| gemini-3.8-flash 일반 | 4 → 7 | 3 → 2 | 4 / 7 |
| claude-opus-5-5 | 4 → 5 | 2 → 4 | 3 / 4 |

- 시간대 관련 오류가 줄지 않았다. 오퍼스는 "자료 없음"을 읽고도 "술집은 밤 장사"처럼 업종 상식으로 메웠다 — 사실 문장으로는 업종 일반론을 막지 못한다.
- 결정: 오류가 늘어 **운영에 넣지 않았다**.
- 부수 발견: 숫자 금지 규칙 때문에 동 이름 속 숫자를 한글로 풀어 쓴다("이태원제일동", "답십리제두동") — 3.8은 매 회차 116건 중 약 11건. 대부분 뜻은 통하지만 "제두동"처럼 없는 지명이 되면 오류로 잡힌다. 숫자 가드는 이미 동 이름을 검사에서 빼므로(v0.68.0) 지시문에서 "동 이름은 본문 표기 그대로"를 허용하는 것이 다음 후보다.

### 7단계 — 동 이름은 본문 표기 그대로(v0.76.1, 적용)

6단계에서 찾은 "숫자 금지 때문에 동 이름을 한글로 풀어 씀"을 고쳤다 — 숫자 금지 규칙에 "동 이름은 본문에 적힌 그대로 쓴다(예: 역삼1동)" 예외 한 줄(태그 `dong150`).

| 모델 | 동 이름 한글 풀이 | 숫자 가드가 지운 문장 | 핵심 오류 말투만 → +예외 | 짝 비교(전에만 / 후에만) |
|---|---|---|---|---|
| gemini-3.8-flash 일반 | 11 → **0** | 0 → 0 | 4 → **3** | 3 / 2 |
| claude-opus-5-5 | 4 → **0** | 6 → 4 | 4 → 5 | 4 / 5 |

- 목표(없는 지명 방지)를 이뤘고 기본 모델 오류가 늘지 않아 운영에 넣었다(main 머지·8200 재빌드).
- 남은 오류: 본문에 없는 평가("평균 매출이 낮은 편"), 시간대 자료 부족을 동 흐름으로 메움, "경고 없음"을 자료 공백 탓으로 돌림.

### 8단계 — 남은 오류 3유형을 코드로 막기(v0.78.0)

7단계 뒤 남은 오류를 유형별로 지시문이 아니라 코드(사실 문장·가드)로 막았다(태그 `fix150`). 평가셋 facts 116건에는 매출 근거의 서울 중앙값만 다시 채웠다(`freeze --augment`, 다른 값 변화 없음).

| 유형 | 고친 방식 |
|---|---|
| 본문에 없는 매출 평가("평균 매출이 낮은 편") | 매출 줄에 서울 같은 업종 동 중앙값과 견준 등급을 코드가 붙임 |
| 시간대 매출 자료가 없는데 사람 흐름으로 매출 시간 추정 | 자료가 없으면 시간대 낱말+매출·장사 문장을 지우는 가드(모른다고 밝힌 문장은 남김) |
| "경고 없음"을 자료 공백 탓으로 설명 | 판정 줄을 켜짐 / 계산했지만 기준 안 넘음(이름) / 자료 부족(이름)으로 나눔 |

| 모델 | 핵심 오류 7단계 → 8단계 | 짝 비교(전에만 / 후에만) | 가드가 지운 문장 |
|---|---|---|---|
| gemini-3.8-flash 일반 | 3 → 4 | 3 / 4 | 5 |
| claude-opus-5-5 | 5 → 1 | 5 / 1 | 4 |

- 7단계 3.8 오류 3건 중 매출 평가 2건(e064·e100)은 사라졌다. 8단계 3.8 오류 4건은 시간대 이름을 바꿔 옮김(e038, 매출 낱말이 없어 가드 밖), 상권변화지표 반대로 읽음, 없는 자료를 추정, 본문에 없는 판단 — 겨냥한 세 유형은 0건이다. +1은 판정 오차(±3) 안이다.
- 해석 속 "경고 없음… 자료가 비어서" 인과 표현(키워드 집계): 3.8 3 → 1, 오퍼스 6 → 1.

### 9단계 — 상권변화지표 쉬운 뜻·본문에 없는 시간대 낱말 가드, 미적용

8단계 뒤 남은 오류 중 "상권확장을 침체로 읽음"(e082)과 "밤을 저녁·주말로 바꿔 옮김"(e038)을 코드로 막아 봤다(태그 `fix2-150`, 브랜치 `feat/answer-fixes-2`, 미머지).
상권변화지표 이름 뒤에 쉬운 뜻(예: "정체(영업 중·폐업 점포 모두 서울보다 오래 영업 — 오래된 가게 위주로 변화가 적은 쪽)")을 붙이고, 해석에 본문에 없는 시간대 낱말(저녁·점심·퇴근 등)이 나오면 그 문장을 지웠다.

| 모델 | 핵심 오류 8단계 → 9단계 | 짝 비교(전에만 / 후에만) |
|---|---|---|
| gemini-3.8-flash 일반 | 4 → 5 | 4 / 5 |
| claude-opus-5-5 | 1 → 5 | 1 / 5 |

- 쉬운 뜻이 새 오류를 낳았다: "오래된 가게 위주"를 읽고 "상권이 굳어 새로 들어가기 어렵다"를 덧붙였다(3.8 e001·e016). 뜻풀이도 해석의 재료가 된다.
- 오퍼스 오류 5건 중 4건은 시간대 매출 자료가 없는데 "저녁 손님이 많다"처럼 **손님**으로 매출 시간을 메운 것 — 본문에 있는 시간대(저녁) 낱말이라 새 가드 밖이고, 8단계 시간대 매출 가드는 "손님"을 넣으면 지나치게 지워 뺐다.
- 결정: 오류가 늘어 **운영에 넣지 않았다**. 8단계 오퍼스 1건은 판정 오차 쪽으로 낮게 나온 값으로 본다.

### 10단계 — 시간대 매출을 모르면 해석 입력에서 사람 흐름 빼기, 미적용

9단계 뒤 가장 많이 남은 오류는 시간대 매출 자료가 없는데 본문의 "사람 흐름: 가장 많은 때 저녁"을 "저녁 손님이 많다"로 옮기는 것이었다. 원인을 없애려고, 시간대 매출 자료가 없을 때 **모델에 주는 입력에서만** 사람 흐름 구절을 뺐다(화면 본문은 그대로, 태그 `flow150`, 브랜치 `feat/hour-flow-input`, 미머지).

| 모델 | 핵심 오류 8단계 → 10단계 | 그중 시간대 관련 | 짝 비교(전에만 / 후에만) |
|---|---|---|---|
| gemini-3.8-flash 일반 | 4 → 6 | 1 → 4 | 2 / 4 |
| claude-opus-5-5 | 1 → 6 | 1 → 4 | 0 / 5 |

- 새 오류 유형이 생겼다: 입력에 사람 흐름이 없으니 "사람이 언제 많은지는 자료가 부족하다"고 썼는데, 화면 본문에는 사람 흐름이 있어 **본문과 어긋난다**(e038·e082·e104). 모델 입력과 화면이 다르면 그 차이가 오류가 된다.
- 결정: 오류가 늘어 **운영에 넣지 않았다**.
- 시간대 매출 오류에 대해 지금까지 시도한 세 방법 — 사실 문장 추가(6단계), 시간대 낱말 가드(9단계), 입력에서 빼기(10단계) — 모두 오류를 늘렸다. 8단계(v0.78.0)의 시간대 매출 가드("시간대 낱말 + 매출·장사")까지가 효과가 확인된 선이다. 남은 "저녁 손님" 유형은 판정 오차 수준(116건 중 1건 안팎)이라 더 손대지 않는다.

### 11단계 — 뉴스를 본문(해석 입력)에서 빼기·상권 축소 신호 제거(v0.83.0, 이용조건상 필수)

네이버 검색 API 특약(AI 입력 금지)에 따라 리포트 본문에서 뉴스 줄과 유사 사례의 뉴스 건수 문장을 빼고, 해석 지시문의 뉴스 규칙 한 줄도 뺐다. 같은 때 판정 신호 "상권 축소"가 빠져 왜 안 되나 절의 참고 신호 줄도 없어졌다(태그 `news150`, 브랜치 `feat/news-compliance`).

| 모델 | 핵심 오류 8단계(fix150) → 11단계 | 짝 비교(전에만 / 후에만) |
|---|---|---|
| gemini-3.8-flash 일반 | 4 → 9 | 4 / 9 |
| claude-opus-5-5 | 1 → 4 | 1 / 4 |

- 겹치는 오류 시나리오가 하나도 없다. 해석 글이 크게 바뀌었고(같은 시나리오끼리 유사도 0.4~0.8, 글자까지 같은 것 150건 중 34건 — 대부분 LLM을 안 부르는 자료 부족 시나리오) 판정자 기준도 흔들렸다.
- 3.8의 9건 중 4건(e024·e045·e050·e111)과 오퍼스 1건(e141)이 "조기 폐업(문 닫은 점포의 영업 기간)을 새로 연 점포의 생존율로 풀이" 유형이다. 8단계 판정자는 같은 유형을 핵심 오류로 보지 않았다(e141 오퍼스 메모). 이 유형을 빼면 3.8 4 → 5, 오퍼스 1 → 3으로 판정 오차(±3) 안이다.
- 나머지는 본문에 없는 인과(e046·e048 "많아서 조기 폐업", e039 원인 설명)·시간대 옮김(e015·e077·e078)·자료 부족을 추정으로 메움(e058)이다.
- 결정: 이용조건상 되돌릴 수 없는 변경이라 **적용**한다. 조기 폐업 오독은 다음 개선 후보(코드 가드나 본문 정의 문장).

### 12단계 — 지역 사건 줄을 조건 절에 넣기(v0.86.0, 적용)

조건 절에 "[확인된 사실] ○○동 지역 사건(최근 3년, 서울 열린데이터광장): 2025-08 … (출처: OA-xxxxx)" 줄을 넣었다(정비사업 이주·착공, 대규모점포 개설·폐업, 1,000세대 이상 입주 — 최대 5건, 날짜는 달까지). 평가 facts 150건에 한 번 채웠고 사건이 있는 시나리오는 40건(LLM 판정 대상 116건 중 34건). 태그 `events150`, 기준선은 11단계 `news150`.

| 모델 | 핵심 오류 11단계 → 12단계 | 사건 줄 있는 34건 안 |
|---|---|---|
| gemini-3.8-flash 일반 | 9 → 3 | 5 → 3 |
| claude-opus-5-5 | 4 → 2 | 1 → 2 |

- 해석이 사건을 언급한 건 3.8 3건·오퍼스 5건(34건 중)뿐이고, 그중 오류는 없다. 남은 핵심 오류(e013·e028·e033·e114)는 모두 기존 유형(업종 시간대 자료 부족을 일반론으로 메움, 신호 사이 인과 지어냄, 순유출 기준 미달을 개폐업 수로 단정)이다.
- 3.8 9 → 3은 판정자 변동이 크다(11단계 오류 시나리오와 겹침 거의 없음). 결론은 "늘지 않았다"까지만 — 기본 모델 오류가 늘지 않아 **적용**.

### 13단계 — 판정 근거 약함 표시(v0.87.0, 적용) · 조기 폐업 오독 가드(미적용)

두 가지를 함께 시험했다(태그 `weak150b`, 기준선 12단계 `events150`). ① 안정 신호 없는 7개 업종에 비추천을 내지 않고 판정 줄에 "판정 근거 약함" 문장(평가 facts 74건에 반영, 그중 비추천 12건 → 조건부). ② 해석에서 "조기 폐업"을 새로 연 점포의 생존으로 풀이한 문장을 지우는 가드 — 첫판(`weak150`)은 생존 절벽·조기 폐업을 한 문장에 바르게 푼 문장까지 25개를 지워 "조기 폐업" 앞뒤 구만 보도록 고친 뒤 다시 돌렸다(3.8 5문장·오퍼스 4문장 삭제).

| 모델 | 핵심 오류 12단계 → 13단계 |
|---|---|
| gemini-3.8-flash 일반 | 3 → 5 |
| claude-opus-5-5 | 2 → 4 |

- 3.8의 늘어난 2건: e036은 "판정 근거 약함"을 빼고 위험을 확실하다고 단정(①), e050은 가드가 "저녁 매출이 하루 평균보다 높다"와 오독이 섞인 첫 문장을 통째로 지워 직접 답의 근거가 사라졌다(②). 나머지는 기존 유형(시간대 자료 부족 메움·신호 사이 인과·없는 사실 보탬).
- 오퍼스 e041은 가드가 못 잡은 조기 폐업 오독이다.

- 95% 구간: 문항 단위 bootstrap(같은 문항 3회를 한 묶음으로) 4,000회.
