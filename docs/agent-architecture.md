> 전제 문서: `docs/brainstorming.md`(제품 설계), `CLAUDE.md`(아키텍처 원칙), `docs/api.md`(데이터 소스)

## 1. 설계 원칙 3가지

### 1-1. 에이전트는 "업종별"이 아니라 "분석 축별"로 나눈다

업종은 brainstorming §3.5의 확정대로 **Strategy/설정으로 분리**한다 (업종-불가지론 파이프라인, `if 업종` 분기 금지). 에이전트 경계는 §5.3의 설계 원칙 — **"전통 변수(기초체력)와 특이변수(외부 충격)를 분리된 축으로"** — 를 그대로 따른다. 이렇게 하면 프로젝트의 핵심 차별점(기초체력 vs 충격 취약도 분리 제시)이 아키텍처 수준에서 강제된다.

### 1-2. 숫자는 결정론, 에이전트는 해석

폐업률·성장률·경쟁밀도 등 모든 지표는 **백엔드 배치가 산출해 집계 테이블에 저장**한다 (brainstorming §7.2 — 집계 테이블 1개 = Fractal 11-File Set 1개). LLM은 숫자를 계산하지 않는다. 에이전트의 역할은 세 가지뿐:

- **검색(retrieval)**: 정형 지표 조회, RAG 코퍼스 검색, 뉴스 검색
- **판단(judgment)**: 회복 vs 소멸 판별, 공고-사용자 적합성 매칭
- **합성(synthesis)**: 근거 인용을 포함한 리포트 작성

계산기(§8.1 ②③)도 동일 — 순수 계산 로직은 도구(코드)이고, 에이전트는 입력을 모아 호출하고 결과에 상권 리스크 문맥을 붙인다.

### 1-3. Port = Tool (헥사고날과의 접점)

CLAUDE.md 헥사고날 원칙상 **에이전트는 또 하나의 Driving Adapter**다. REST Router가 UseCase(input port)를 호출하듯, 에이전트의 tool이 같은 UseCase를 호출한다:

```
[REST Router]  ──┐
                 ├──→ Input Port (UseCase) ──→ Interactor ──→ Output Port ──→ Repository
[Agent Tool]   ──┘
```

- Fractal 11-File Set을 테이블마다 만들면 **에이전트 도구가 하나씩 자동으로 생긴다.**
- 도구 정의(name / description / input_schema)는 UseCase 인터페이스에서 기계적으로 도출한다.
- 에이전트의 실수는 Port 계약 안에 갇힌다 — "AI 위임 단위 = Bounded Context"의 런타임 연장.
- **LLM 제공자·임베딩·리랭커도 Output Port 뒤에 둔다**: `LLMGatewayPort`, `EmbeddingPort`, `RerankerPort`. 로컬 ↔ EC2 ↔ 상용 API 전환은 어댑터 교체(DI 설정)로 끝난다.

## 2. 에이전트 구성: 오케스트레이터 + 전문가 3

| 에이전트 | 담당 (근거) | 주 도구 | 모델 |
|---|---|---|---|
| **오케스트레이터** | 질문 해석 → 전문가 호출 → 종합 리포트 합성, **응답 규칙 집행** | 전문가 3 에이전트 | 상위 모델 |
| **① 상권 진단** | 기초체력: 경쟁밀도·개폐업률·생존율·배후인구·임대료 (§5.1) | 정형 지표 조회 UseCase (SQL 기반) | 중간 모델 |
| **② 충격·정책 분석** | 특이변수 4계층: 거리두기·금리·트렌드·지역 이벤트 (§5.2~5.4), 회복 판정 | 시계열 조회 + 뉴스 검색 | 중간 모델 |
| **③ 정책자금·금융** | 공고 매칭(RAG) + 창업비용·월세vs매입 계산기 (§8) | 공고 RAG + 계산기 UseCase | 중간 모델 |

- 위임 패턴: 표준 **orchestrator-worker** — 전문가 에이전트를 오케스트레이터의 도구로 노출. 전문가 3개는 병렬 실행 가능 (지연시간 상쇄).
- 에이전트 루프 구현: **Anthropic SDK Tool Runner** (자체 호스팅 FastAPI 백엔드에서 루프 실행). 서버 호스팅형(Managed Agents)은 온프레미스 방침과 맞지 않아 제외.

### 2-1. 응답 규칙 (오케스트레이터 시스템 프롬프트에 집중)

개별 에이전트가 아니라 오케스트레이터 한 곳에서 집행한다:

1. **외국인 변수 금지 규칙** (§5.2): "외국인 비율 높음 = 나쁜 상권" 류 출력 금지 — 항상 "업종 타겟과의 정합성" 문맥으로만.
2. **지원금 왜곡 보정** (§5.2 ①): 재난지원금·손실보상 기간의 낮은 폐업률을 회복으로 해석하지 않도록 명시.
3. **금융 규제 경계** (§8.2): 대출 중개·특정 은행 상품 추천 금지, 금리·한도는 공고 원문 인용만, "예상치" 고지 필수.
4. **신뢰 등급 표기** (§5.3): 정형 지표 = "확인된 사실", 뉴스 신호 = "참고 신호" 구분 표기.

### 2-2. 최종 결과물: 종합 리포트 1장

사용자 질문("○○동에서 카페 창업해도 될까?") → 다음 5개 섹션, **전 항목 근거 인용**:

1. **기초체력 스코어카드** (①): 경쟁밀도·개폐업·배후인구·임대료, 수치 근거 포함
2. **충격 취약도·회복 판정** (②): V자/L자/소멸 판별 + 근거 시계열
3. **교차 시그널** (§3.5, post-MVP — 자리만 확보): 인접 업종 신호
4. **자금 조달 카드** (③): 매칭 공고 요약 + 원문 링크, 계산기 결과
5. **지도 뷰 연결**: 해당 행정동 단계구분도 딥링크 (§7)

멀티에이전트의 제품 가치 = **트레이스 투명성**. 각 항목이 "어느 에이전트가 어떤 데이터로" 판단했는지 남으므로 신뢰 등급 표기가 UI로 자연 구현된다.

## 3. 구축 순서 (10주 계획 내 배치)

멀티에이전트를 먼저 만들지 않는다. 도구(Port)가 완성된 뒤 분리한다.

| 시기 | 작업 |
|---|---|
| ~6주차 | 기존 계획대로: 데이터 파이프라인 + 지표 산출 배치 + **도구(UseCase) 완성** — 이 산출물이 곧 에이전트 도구 |
| 7~8주차 | **단일 에이전트 + 전체 도구**로 엔드투엔드 구동. Hybrid RAG Chunking + Recall@5 평가셋 |
| 9주차 | 오케스트레이터-전문가로 **분리** — 도구가 Port 기반이므로 재작성이 아니라 오케스트레이션 리팩토링 (도구의 에이전트 배정만 변경) |
| 10주차 | AWS 배포 + 평가 + 데모 (§5 인프라 일정과 연동) |

**평가 분리**: Recall@5 91.5%는 **검색(RAG) 도구 단위 지표**로 측정 (§9-4 평가셋). 에이전트 전체는 별도의 엔드투엔드 응답 평가. Latency -40%는 지표 사전 계산(에이전트 호출 수 감소) + 전문가 병렬 실행으로 달성.

## 4. AWS 인프라 ($400 크레딧 운용)

### 4-1. 운용 원칙 (확정)

- **10월 초중순까지: 전액 로컬 개발.** 각 모델(임베딩·리랭커·보조 LLM)은 로컬에서 개별 기능 테스트 가능.
- **프로젝트 종료 2주 전부터 EC2 배포** — 여러 모델이 병렬로 상시 구동되는 구간. 지출을 이 2주에 집중하면 $400으로 GPU 병렬 서빙이 여유 있음.
- **S3**: `data/raw/` 아카이브 백업(MANIFEST SHA256과 함께) + 모델 가중치 캐시 + 평가 결과. 비용 $5 미만.
- 에이전트 두뇌(오케스트레이터·전문가)는 상용 API, **물량 작업(임베딩·리랭킹·구조화 추출·평가)은 EC2** — 품질과 예산의 분담.

### 4-2. 마지막 2주 예산 계획 (서울 리전 ap-northeast-2, 대략치)

| 구성 | 시간당(스팟) | 2주(≈336h) 상시 |
|---|---|---|
| g5.xlarge (A10G 24GB) — 보조 LLM 서빙 | ~$0.4~0.5 | ~$150~170 |
| g4dn.xlarge (T4 16GB) — 임베딩+리랭커 동거 | ~$0.25~0.3 | ~$90~100 |
| CPU 1대 — 게이트웨이·모니터링 | ~$0.1 | ~$35 |
| S3 + 트래픽 + 기타 | — | ~$10 |
| **합계** | | **~$300** (여유 ~$100은 리허설·발표 당일 온디맨드 전환용) |

**병렬 배치 기준 = VRAM**: 임베딩(BGE-M3급 ~2-3GB) + 리랭커(~2GB)는 T4 16GB 한 대 동거. 7~8B LLM은 4bit ~8GB(T4 가능) / fp16 ~16GB(A10G 필요). 무거운 모델당 GPU 1대 + 가벼운 모델 동거.

**추가 이점**: 서울 리전 EC2 = 국내 IP → 온프레미스 장애 시 공공 API 수집 백업 서버 겸용 가능 (api.md §6-1 국내 IP 제약 대응).

### 4-3. 리스크 대비책 4가지

1. **GPU 쿼터 증설 신청은 지금** (최우선 액션). 개인/신규 계정은 G 계열 vCPU 쿼터 기본 0 → Service Quotas에서 온디맨드·스팟 각각 증설 신청. 승인에 며칠 소요, 신청만으로는 무과금.
2. **발표 당일은 스팟 금지.** 2주 구동은 스팟, 리허설~발표 당일(1~2일)만 온디맨드 전환 (~$50, 여유분에서 충당).
3. **로컬-EC2 동형성은 Docker로 보장.** 서빙 스택(vLLM/TEI 등)을 처음부터 docker-compose로 구성 — 로컬과 EC2의 차이는 `.env`의 엔드포인트 URL 하나. 이전 작업 = 이미지 pull + compose up. Port/어댑터 코드는 불변, DI 설정만 교체.
4. **9월 중 하루짜리 스모크 배포 1회** (<$5). 스팟 GPU 몇 시간 기동 → 온프레미스 백엔드 → EC2 임베딩 → pgvector 검색 → 응답까지 전체 관통 테스트. 쿼터·보안그룹·CUDA AMI·네트워크 문제를 미리 소거.

### 4-4. 비용 가드레일

- AWS Budgets 알림: $150 / $300 두 단계.
- 모든 LLM 호출의 `usage`(입출력 토큰)를 DB에 로깅 → 에이전트별 비용 가시화 (튜닝 근거 + 발표 자료의 "리포트 1건당 비용" 수치).
- EventBridge 스케줄러로 개발 기간 GPU 야간 자동 중지 (켜둔 채 방치 시 하루 $20~30 소실).

## 5. 열린 질문 (팀 결정 필요)

1. 에이전트 두뇌용 상용 LLM API의 선택과 비용 부담 주체 (AWS 크레딧은 EC2/S3 용도로 확정)
2. 임베딩 모델 선정: BGE-M3 vs 한국어 특화(KURE 등) — Recall@5 평가셋으로 비교 후 확정
3. 보조 LLM(구조화 추출·평가용) 오픈모델 선정 및 품질 검증 기준
4. EC2 ↔ 온프레미스 통신 방식: 보안그룹 IP 허용 vs Tailscale
